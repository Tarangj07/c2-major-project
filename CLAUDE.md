# CLAUDE.md

## 1. Project Identity

This repository implements an academic digital-forensics research framework for an M.Tech Cyber Security dissertation.

### Research Topic

**Forensic Reconstruction and Process-Level Attribution of Encrypted C2 Communications Using Memory–Network Correlation**

The project studies how encrypted C2 communications can be reconstructed and attributed to originating processes by correlating:

* Network traffic captured in PCAP
* Volatile memory artifacts
* Process information
* Socket/network ownership information
* TLS metadata
* Temporal relationships between memory and network evidence

This is a **controlled defensive forensic research project**.

The system must not become an operational malware/C2 framework.

---

# 2. Research Questions

The implementation must support evaluation of:

* **RQ1:** How accurately can encrypted network connections be attributed to originating processes using volatile-memory artifacts?
* **RQ2:** What C2-related forensic artifacts can be recovered from volatile memory that encrypted network traffic alone cannot provide?
* **RQ3:** How does artifact recoverability change over time, including after connection closure and process termination?
* **RQ4:** How do controlled anti-forensic behaviors affect recovery and attribution?

The research contribution is the **explainable correlation between memory evidence and network evidence**, not merely running Volatility or tshark.

# 9. Evidence Integrity

Evidence must be treated as immutable.

Primary evidence includes:

```text
PCAP
Memory image
Ground-truth experiment metadata
```

For every evidence file:

* Record SHA-256 hash.
* Preserve the original.
* Never analyze by modifying the original.
* Prefer working copies for processing.
* Record acquisition timestamps.
* Record experiment ID.
* Record relevant environment metadata.

The forensic pipeline must never silently alter source evidence.

---

# 10. Ground Truth

Ground truth is separate from forensic inference.

Ground truth may include:

* Known client process PID
* Known executable name
* Known server IP
* Known server port
* Known client IP
* Known connection start/end time
* Known experiment ID
* Known event timestamps

Ground truth must come from the controlled experiment and must not be generated by the correlation engine.

The correlation engine must not use ground-truth PID/process information as an input merely to make attribution succeed.

Ground truth is used **afterward for evaluation**.

# 13. Phase 4 — Correlation and Attribution

Phase 4 is the next implementation phase.

The goal is to correlate:

```text
PCAP NetworkFlow
        +
Memory SocketArtifact
        +
Memory ProcessArtifact
        ↓
Correlation Engine
        ↓
Attribution Candidate(s)
        ↓
Explainable Evidence
```

The engine must answer:

> Which process, if any, is supported by the available memory evidence as the owner/originator of the network connection observed in the PCAP?

---

# 14. Correlation Must Be Explainable

Do not implement a black-box attribution score without evidence.

Every attribution result must be explainable.

A result should be able to state, conceptually:

```text
Candidate PID: 4580

Supporting evidence:
- Memory socket matched local IP
- Memory socket matched local port
- Memory socket matched remote IP
- Memory socket matched remote port
- Protocol matched
- Temporal relationship satisfied
- Process artifact exists

Confidence:
HIGH / MEDIUM / LOW

Evidence:
<references to specific memory/network artifacts>
```

The exact schema may be designed during Phase 4.

### Temporal relationship


Do not require every field to exist.

Missing evidence must be represented explicitly rather than silently treated as a match.

# 16. Canonical Flow Identity

Network and memory socket observations should be normalized into a direction-aware or canonical representation suitable for comparison.

Do not rely on textual formatting.

The correlation implementation should correctly handle:

* IPv4
* IPv6 where supported
* TCP
* UDP where supported
* different endpoint ordering
* missing ports
* closed sockets
* partial memory evidence

---

# 17. Multiple Candidates

The engine must not assume exactly one candidate.

Possible outcomes:

```text
MATCHED
MULTIPLE_CANDIDATES
NO_MATCH
INSUFFICIENT_EVIDENCE
```

If multiple memory processes appear consistent with a network flow, preserve the ambiguity.

Do not arbitrarily select a PID merely because one candidate appears first.

---

# 18. Negative Controls

Phase 4 should support negative-control experiments.

Examples:

* Similar network flow with no corresponding memory socket
* Memory socket with no corresponding PCAP flow
* Same remote endpoint but different local port
* Same local endpoint but different remote endpoint
* Temporally incompatible socket
* Unrelated process with similar metadata

The correlation engine must avoid producing false attribution from weak similarities.

---

# 20. TLS Handling

The research concerns encrypted C2.

Therefore:

* Do not claim encrypted application payload was recovered when it was not.
* TLS metadata may be used as observable evidence.
* SNI, TLS version, cipher information, certificate metadata, and handshake observations may be correlated.
* TLS Application Data must not be treated as plaintext.
* Absence of TLS handshake observations must remain explicit.
* Do not invent decrypted content.
* Do not infer commands from encrypted payload bytes.

Any future reconstruction must clearly distinguish:

```text
Observed
Derived
Inferred
```
