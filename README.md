# Encrypted C2 Forensic Reconstruction Framework

A research-grade, modular forensic analysis pipeline for controlled laboratory
experiments involving encrypted C2 communication. The framework correlates
volatile-memory artefacts with captured network traffic to attribute encrypted
flows to their originating processes.

> **Scope.** This is a defensive digital-forensics research project. It is
> designed to analyse evidence generated by a controlled laboratory C2
> simulator. It is **not** designed to interact with real-world C2
> infrastructure, deploy any operational capability, or be used offensively.

## Research questions

- **RQ1 — Attribution.** How accurately can encrypted network connections
  be attributed to their originating processes using volatile-memory
  artefacts?
- **RQ2 — Reconstruction.** What C2-related forensic artefacts can be
  recovered from volatile memory that cannot be obtained from encrypted
  network traffic alone?
- **RQ3 — Persistence.** How does the recoverability of C2 artefacts
  change over time, including after connection closure and process
  termination?
- **RQ4 — Anti-forensics.** How do controlled anti-forensic behaviours
  affect C2 artefact recovery and process-level attribution?

## Phase 1 + Phase 2 + Phase 3 status

This commit ships **Phases 1, 2, and 3** of the planned
development order.

Phase 1:

- repository layout
- configuration loading
- typed data models
- experiment metadata and ground-truth handling
- SHA-256 evidence hashing
- CLI skeleton (`init`, `show`; later phases are placeholders)
- unit-test infrastructure
- architecture documentation

Phase 2 (PCAP extraction):

- `c2forensics pcap acquire EXP001 <source>` — copy + hash
- `c2forensics pcap extract EXP001` — run tshark, parse, persist
- deterministic `NetworkEvidence` bundle (flows + TCP lifecycle +
  TLS observations)
- `ParseDiagnostics` for malformed/partial PCAPs
- explicit OBSERVED / DERIVED / INFERRED boundary in
  `docs/pcap-extraction.md`. The Phase 2 output contains zero
  inferred fields; process attribution belongs to Phase 4.

Phase 3 (memory extraction):

- `c2forensics memory acquire EXP001 <image>` — bit-for-bit copy
  + hash; refuses symlinks, empty files, overwrites
- `c2forensics memory extract EXP001` — runs the supported
  Volatility 3 plugins (`windows.pslist.PsList`,
  `windows.netscan.NetScan`) and persists a typed bundle
- `c2forensics memory status EXP001` — show on-disk images and
  the latest extraction
- deterministic `MemoryExtractionResult` bundle (processes +
  sockets + explicit-absence TLS) with positional provenance
  alignment
- explicit OBSERVED / DERIVED / INFERRED boundary in
  `docs/memory-extraction.md`. The Phase 3 output contains zero
  inferred fields; memory-to-PCAP attribution belongs to
  Phase 4.
- Real-Volatility integration test skips cleanly on hosts
  without `vol`; on a host where Volatility 3 is installed and a
  real Windows memory image is supplied, the test runs the real
  subprocess.

Correlation, reconstruction, timeline, persistence,
anti-forensics, and evaluation remain **explicitly out of scope**
and will be implemented in later phases per the dissertation
plan.

## Quick start (development)

```bash
# From the repository root
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

# Run the test suite
pytest
```

The CLI entry point is registered as `c2forensics` once the project is
installed. From a development checkout you can also invoke it via
`python -m c2forensics.cli.main`.

```bash
c2forensics --version
c2forensics init EXP001
c2forensics show EXP001
```
