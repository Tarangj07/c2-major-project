# Experiment protocol

## Layout

```
experiments/
└── EXP001/
    ├── metadata.json
    ├── ground-truth.json           # optional; produced by the simulator
    │
    ├── raw/
    │   ├── capture.pcap
    │   └── memory/                 # memory dumps go here
    │
    ├── extracted/                  # PCAP and memory extractor output
    ├── normalized/                 # framework-normalised evidence
    ├── correlation/                # correlation results
    ├── reconstruction/             # C2 case JSON
    ├── timeline/                   # timeline events
    └── evaluation/                 # metrics
```

The framework never overwrites anything under `raw/`. Files under the
other directories are derived products and may be regenerated by
re-running the relevant pipeline stage.

## Creation

```bash
c2forensics init EXP001 \
    --description "baseline run" \
    --target-host 192.168.56.108 \
    --c2-server-host 192.168.56.20 \
    --c2-server-port 8443 \
    --tag baseline --tag rq1
```

This creates the directory tree and a `metadata.json` with the
initialised status, current UTC timestamp, and a configuration
snapshot.

## Inspection

```bash
c2forensics show EXP001
```

Prints the metadata as JSON. Use this to verify the experiment was
initialised correctly and to record its metadata hash in a lab
notebook.

## Raw evidence acquisition

Acquisition is out of scope for Phase 1. Once the PCAP and memory
acquisition stages are implemented, the framework will:

1. Place the captured PCAP at `experiments/EXP001/raw/capture.pcap`;
2. Place memory dumps under `experiments/EXP001/raw/memory/`;
3. Hash every file under `raw/` and store the digests in
   `metadata.json.raw_hashes`.

The framework will never modify files under `raw/` after acquisition.

## Ground truth

The C2 simulator records ground truth separately, in
`experiments/EXP001/ground-truth.json`. The forensic pipeline never
reads this file; only the evaluation stage does. The ground-truth
schema is defined by `c2forensics.models.experiment.GroundTruth`.

## Status transitions

`ExperimentStatus` values are intended to be monotonic:

```
INITIALIZED
  → EVIDENCE_ACQUIRED
  → EXTRACTED
  → NORMALIZED
  → CORRELATED
  → RECONSTRUCTED
  → TIMED
  → EVALUATED
  → COMPLETED
```

A `FAILED` state is recorded if a stage raises and the user opts not to
retry. The framework does not auto-promote state; each stage calls
`update_status(...)` when it completes successfully.
